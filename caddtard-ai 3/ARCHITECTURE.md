# CADDTARD AI v3.0 — Architecture & Honesty Map

This document maps every layer of the requested six-layer architecture, plus the
v3.0 operational layer, to what
is **implemented and running**, what is **scaffolded** (a real, typed
interface and database row exists, but no live logic sits behind it yet), and
what is **future work**. The full enterprise spec — ~100 agents, ~31 live
data sources, a Kubernetes/Temporal/GPU production stack — is realistically a
multi-year, multi-engineer build. This codebase is a genuine v2.0 foundation:
every "implemented" item below calls a real external API or runs real logic
against a real database, and nothing in this document claims more than the
code actually does.

Counts below were generated by importing `app/seed_data_v2.py` directly and
counting rows — they are exact, not estimates.

## Layer 2 — Scientific Knowledge Graph

**Status: real, running, Postgres/SQLite-backed. Neo4j is a documented
swap-in, not yet done.**

`app/graph/store.py` defines a `GraphStore`-shaped interface
(`upsert_node`, `upsert_edge`, `nodes`, `neighbors`, `subgraph`) implemented
today by `PostgresGraphStore` over two relational tables (`graph_nodes`,
`graph_edges`) with typed `node_type`/`edge_type` columns, JSON properties,
and a `version` column for future change-tracking. Subgraph traversal is a
real breadth-first search, implemented in Python so it runs identically on
SQLite (local dev) and Postgres (Docker).

Seeded content: **28 nodes** (13 genes, disease/phenotype nodes, the shared
V-ATPase pathway node, and drug/compound nodes) and **28 edges**
(`pathogenic_for`, `part_of_pathway`, and other typed relationships), each
edge carrying a real supporting citation in its properties. Exposed via
`GET /api/graph/nodes`, `GET /api/graph/nodes/{id}/subgraph`, and the
dashboard-friendly `GET /api/graph/genes/{symbol}/subgraph` — rendered live
in the dashboard with Cytoscape.js.

**Why not Neo4j today:** this sandbox has no outbound access to PyPI, so a
`neo4j` driver could not be installed or tested here. Swapping in
`Neo4jGraphStore` behind the same interface (already documented in
`store.py`'s docstring) does not require touching any router or frontend
code — the `docker-compose.yml` `neo4j` service (behind the `extended`
profile) is included so this can be stood up and wired in next.

The 20 implemented agents run on APScheduler with intervals read from the
`agent_definitions` table (`GET /api/agents`, filterable by `division` and
`status`), and every run is recorded in `agent_runs` with status/summary —
visible per-agent in the dashboard and via `GET /api/agents/{key}/runs`. Each
agent function is wrapped in a shared `agent_run` context manager so an
external API failure is caught and logged, never crashes the scheduler.

The other 40 (of 60) are real rows (not just prose) — each has a `division`,
`description`, and `status="planned"` — so the target org chart from the spec
is fully represented and queryable, and can be implemented incrementally
without a schema change.

## Layer 4 — Scientific Reasoning Engine

**Status: real, running. 3 hypothesis chains, 11 total steps, seeded for the
three selected candidates.**

`Hypothesis` → `HypothesisStep` models an explicit, directional causal chain
(e.g., Hypothesis 17: ATP6V0C loss of function → decreased lysosomal
acidification → autophagy failure → mTOR dysregulation → synaptic
dysfunction → epileptic encephalopathy). Every step carries its own
`confidence` (0–1), `supporting_papers`, `conflicting_evidence`,
`experimental_status`, and `recommended_next_experiment` — nothing is a
single free-text answer. `overall_confidence` is computed on read (mean of
step confidences), so it can't silently drift out of sync with the steps.
Exposed via `GET /api/hypotheses` (filterable by candidate/gene) and rendered
as an evidence trail in the dashboard, each step showing its confidence pill
and linked papers.

## Layer 5 — Laboratory Operating System

**Status: real CRUD API against `Experiment`/`Protocol`/`ReagentItem`/
`NotebookEntry`/`AssayResult`. No physical instrument is connected — there is
no lab behind this API — but the data model matches the instrument
categories named in the spec (sequencing, microscopy, flow cytometry, ELISA,
western blot, LC-MS, animal studies) and can accept data from those systems
today via `POST /api/lab/experiments/{id}/results`.**

The literal "AI recommends the next experiment" requirement is implemented
as a direct, traceable readout — not a black-box model: `GET
/api/lab/recommendations` pulls every non-`validated` `HypothesisStep`'s
`recommended_next_experiment` from Layer 4, sorted by ascending confidence
(weakest-evidenced links surfaced first), each with a `reason` string naming
the exact hypothesis and link it came from.

## Layer 6 — Executive Dashboard

**Status: real, running, aggregates live data from Layers 1–5 — not a
separate "dashboard database."**

`GET /api/dashboard/health/{slug}` and `GET /api/dashboard/health` compute,
per candidate, in real time: IND-readiness checklist completion %, average
hypothesis confidence, a documented open-risk-flag count, in-progress/
completed experiment counts, milestone count, and the existing
commercial/patient/CMC/feasibility composite score. The dashboard frontend
renders this as a portfolio view at the top of the page, plus dedicated
sections for the data fabric registry, the full agent taxonomy (with
division/status filters), the knowledge graph (Cytoscape.js pathway map),
the reasoning engine, and the lab log/recommendations feed — all served
same-origin from the FastAPI app, no separate frontend deployment needed.

## Layer 7 — Operational Layer (v3.0, new)

**Status: real schema, real import validation, real evaluation logic — no
live external data source exists for CRO capabilities, vendor quotes, or
CMC/nonclinical packages, so this layer is deliberately import-then-score,
not agent-polled. This is the same design constraint the industry plan this
build was benchmarked against uses, and it's the correct one: nobody
publishes a live feed of "what a CRO will charge you."**

`CroVendor` / `VendorQuote` / `Study` / `StudyMilestone` / `Sample` /
`ChainOfCustodyEvent` / `AssayAcceptanceCriterion` / `AssayAcceptanceEvaluation`
/ `StudyCost` / `GoNoGoDecision` / `ReadinessRequirement` (`app/models_ops.py`)
are populated exclusively through `POST /api/ops/*/import` endpoints, which
accept CSV text matching the templates in `import_templates/` — see
`app/ops_import.py`, which rejects (HTTP 422) any row missing a required
field rather than defaulting it. Every imported row records `imported_from`
so its provenance is always answerable.

Three pieces of this layer are computed, not imported, and the computation
is pure Python with zero SQLAlchemy dependency (`app/ops_logic.py`, unit
tested in `tests/test_ops_logic.py`):

- **Assay acceptance evaluation** (`evaluate_acceptance`): grades a measured
  value against a *prospectively defined* criterion — the criterion must
  exist before the measurement is evaluated against it.
- **Cost variance / budget status**: `None` on zero budget rather than a
  divide-by-zero or a misleading 0%.
- **Go/no-go recommendation** (`compute_go_no_go`): explicitly returns
  `insufficient_data` — not `go` or `no_go` — when no measured evidence
  exists yet. It will not manufacture a confident-looking recommendation
  from zero data. A human reviewer decision (`approved`/`rejected`/
  `deferred`) is a separate, required field (`GoNoGoDecision.human_decision`,
  default `pending`) that only changes through
  `POST /api/ops/go-no-go/{id}/review` — no code path sets it automatically.

**CMC/nonclinical/regulatory readiness** uses one generic
`ReadinessRequirement` table (category discriminates `cmc`/`nonclinical`/
`regulatory`/`ind_cta`) with an explicit `evidence_status` —
`present`/`provisional`/`missing`/`failed`/`not_applicable` — instead of a
single confidence score, so a missing package cannot be silently rendered as
a number that looks like progress. Seeded honestly for the two real
repurposing candidates from the chromoblastomycosis pathway work
(`app/seed_data_v3.py`): 16 of 32 requirement rows are `missing` for
tricyclazole (no pharmaceutical-grade CMC or human safety package exists —
only agricultural-use EPA data), while auranofin (FDA-approved as Ridaura)
carries more `present`/`provisional` rows reflecting its decades of human
safety data. Both candidates' `tropical_disease_prv_eligibility` requirement
is marked `failed`, not `missing` — chromoblastomycosis is confirmed absent
from FDA's section 524 qualifying disease list, a real finding from this
project's own diligence work, not a placeholder.

One demo `Study` (`is_demo=True`, every field labeled `DEMO_SEED`) is seeded
end to end — vendor → quote → sample → chain-of-custody → assay acceptance
criterion+evaluation → cost → go/no-go — using the exact same
`app/ops_import.py` functions the API exposes, so the seed step is itself a
test that the pipeline works, not a separate hand-rolled fixture.

## Continuous operation

The APScheduler background scheduler (`app/agents/scheduler.py`) runs every `implemented`
agent on its own `interval_minutes` for as long as the API process is up —
this is real continuous polling, not an on-demand-only design. The v3.1 MVP
was executed locally with 60 FastAPI tests, a clean Alembic upgrade/check,
all 20 expected scheduler jobs registered, and all standalone schema/logic
verification scripts passing. Its readiness endpoint now verifies database,
scheduler and job-registration state. Actually running continuously on the
internet still requires deploying the Docker image to an always-on host — see
`DEPLOY.md` for concrete
steps against Render or Railway.

## Technology stack: requested vs. actually running here

| Layer | Requested | This build |
|---|---|---|
| Frontend | React + Next.js + TypeScript + Tailwind + Cytoscape.js + Three.js + Plotly | Server-rendered static HTML/CSS/vanilla JS + Cytoscape.js (via CDN) for the graph view. No React/Next.js build pipeline in this sandbox (no npm registry access to install and verify one) — the API contract (`/api/*`, documented at `/docs`) is framework-agnostic, so a React/Next.js frontend can be built against it without any backend changes. |
| Backend | FastAPI + Python + Rust + GraphQL | FastAPI + Python, fully implemented. No Rust component (nothing in this build has a demonstrated need for it yet) and no GraphQL layer (the REST API is complete and documented; GraphQL would be an additive layer over the same models). |
| Data | PostgreSQL + Neo4j + Redis + Elasticsearch/OpenSearch + S3 | PostgreSQL (Docker Compose) / SQLite (local dev) fully implemented and is the system of record, including the graph tables. Neo4j, Redis, and OpenSearch are included as optional Compose services (`--profile extended`) but not yet wired into the API — see Layer 2 above for the Neo4j swap-in plan. No S3/object storage is used since no binary lab files are generated by this build yet; `AssayResult.file_ref` is a ready-made hook for one. |
| AI/ML | PyTorch + HuggingFace + LangGraph + vector DB + ONNX | None implemented. Nothing in this build currently needs a trained model or embeddings — the "AI recommends next experiment" requirement was implemented as a traceable rules-based readout of the reasoning engine (Layer 5) rather than simulating an ML model that doesn't exist. A vector DB would be the natural next step for semantic literature search. |
| Workflow | Docker + Kubernetes + Argo + Temporal + GitHub Actions | Docker + Docker Compose implemented, with healthchecks and `depends_on: service_healthy` gating. No Kubernetes/Argo/Temporal/CI pipeline in this build. |
| Cloud | AWS/Azure + GPU + Terraform | None — this is a portable, self-hosted Docker Compose stack, cloud-deployable to any of AWS/Azure/GCP without code changes, but no cloud-specific IaC was written. |

## Additional capabilities from the spec

RBAC, audit trails beyond `AgentRun`/timestamps, GxP alignment, and formal
FAIR-data tooling are not implemented — they are organizational/compliance
work that sits on top of this API layer once a real user base and regulatory
context exist, not something to fabricate ahead of that need.

## Why this scope, honestly

Fabricating ~100 working agents or a fully populated enterprise knowledge
graph would have produced a demo that looks complete but tells a funder or
collaborator nothing true about what's actually operational. Instead, this
build implements exactly the 12 agents / 12 sources / 3 hypothesis chains /
full CRUD lab log / live portfolio dashboard named above, end to end and
verifiably, and leaves every other named component as a real, typed,
queryable placeholder — so growing from 12 to 52 implemented agents (for
example) is additive work against an existing schema, not a rebuild.
